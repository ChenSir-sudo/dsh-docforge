# 总体架构与推进方式

## 三层能力模型

整个系统按职责切成三层。这个划分不是装饰——它同时决定了**阶段顺序**、**代码边界** 和**验收方式**：内核层用单元测试和轨迹验证，外壳层用接口和端到端验证，运维层用指标和门禁验证。

```text
Agent 内核层：状态 → 图 → 路由 → 知识 → 工具 → 自省
产品外壳层：后端 API → 数据底座 → 队列编排 → 前端 → 人工闭环
工程运维层：安全权限 → 评估门禁 → 部署观测 → 成本灰度
```

```figure arch
@figures/arch.json
```

三层之间是**调用**关系而不是平级关系：外壳层驱动内核层执行，运维层横切两层。 左侧那五类标识不是可选项——它们从阶段零就写进 `AgentState`， 之后每一个节点、每一条日志、每一条审计记录都携带它们。等到阶段十才回头补，代价是重写整条链路。

## 十三阶段演进路线

阶段零到十二按三层归位，每一格只加一个新维度的复杂度。这个顺序本身就是一条**反脆弱路径**： 任何一步失败，你退回上一格，而不是在十几个未验证的变量里排查。

```figure roadmap
@figures/roadmap.json
```

图中的虚线表示「换层」。三条换层规则：

- **同步跑通再异步化**——先用 `invoke()` 验证逻辑，再用队列和 Worker 支撑生产。
- **数据底座先行**——业务库、向量库、缓存、对象存储、checkpointer 是产品化的基础。
- **能观测才上生产**——没有轨迹、指标和告警，就不算生产级 Agent。

# Agent 内核层（阶段零 ～ 阶段五）

内核层回答「Agent 怎么想」。这一层不加任何工程设施：没有数据库、没有队列、没有前端， 只有一个能被 `invoke()` 直接调用的图。这样做的目的是让状态流转的错误在还便宜的阶段暴露。

## 阶段零：需求建模与状态设计

> [!GOAL]
> 在写图代码之前，把业务语言翻译成状态机语言，同时预留产品化所需的字段。

### 关键动作

#### 把业务流程映射为节点清单

节点清单的初始形态是一条直线，后续阶段再在它上面开分支、加回环：

```text
输入解析 → 意图识别 → 知识检索 → 工具调用 → 结果生成 → 质量审查 → 输出/迭代
```

#### 为每个节点标注五类事实

清单定下来之后，逐节点补全下面五项。这一步是后面所有工程决策的依据：

- **输入 / 输出**：读哪些 State 字段、写哪些字段，即节点之间的契约。
- **失败处理**：失败时走降级、重试还是转人工，决定兜底边画在哪。
- **是否幂等**：非幂等节点必须在 State 里留执行标记，交给阶段八去重。
- **是否需要超时**：涉及外部调用的节点一律要有独立超时。
- **是否需要人工审批**：高风险动作提前标记，阶段九接上审批按钮。

#### 定义 AgentState

State 除了 Agent 内核字段，还要预留产品化字段。注意这里已经出现了 `tenant_id`、`user_id`、`session_id`、`job_id` 和 `metadata`——阶段十的安全与多租户就建立在这一段代码上。

```python
class AgentState(TypedDict):
    # Agent 内核
    messages: Annotated[list, add_messages]
    task_params: dict
    user_intent: str
    retrieval_context: list
    tool_results: list
    draft_answer: str
    final_answer: str
    quality_score: int
    iteration_count: int
    max_iterations: int
    error: str | None

    # 产品化字段
    tenant_id: str             # 多租户隔离
    user_id: str               # 用户标识
    session_id: str            # 会话标识
    job_id: str                # 任务标识
    requires_approval: bool    # 是否需要人工审批
    approval_status: str       # pending/approved/rejected
    artifacts: list            # 产出文件/附件引用
    metadata: dict             # 成本、耗时、追踪 ID、模型版本
```

#### 状态设计原则

> 只存可序列化数据；字段语义单一；字段直接支撑控制流和权限决策。

这三条各自对应一类典型事故：存了不可序列化对象，checkpointer 失效；一个字段担两个语义， 条件边写错分支；字段不支撑权限决策，就只能把租户判断散落在节点里。

> [!ACCEPT]
> State 字段覆盖全流程，无节点需要读取未定义字段，所有字段可持久化， **租户 / 用户 / 会话 / 任务标识贯穿始终**。

## 阶段一：最小可运行图

> [!GOAL]
> 验证状态流转机制本身，而不是业务能力。

### 关键动作

先不接 RAG、MCP、数据库、前端。用两个节点加一条边把图跑通。此时你验证的只有一件事： 节点函数能否正确接收并返回 State，归约器是否按预期工作。

```python
workflow = StateGraph(AgentState)
workflow.add_node("generate", generate_node)
workflow.add_node("output", output_node)
workflow.add_edge("generate", "output")
workflow.add_edge("output", END)
graph = workflow.compile()

result = graph.invoke({"messages": [("user", "你好")]})
```

> [!ACCEPT]
> `graph.invoke()` 能返回包含 LLM 回复的 State，无报错。 节点函数正确接收和返回 State，**归约器按预期工作**。

## 阶段二：意图识别与条件路由

> [!GOAL]
> 建立控制流骨架。后续所有能力都往这个骨架上挂。

### 关键动作

1. 意图识别节点读取最新用户消息，通过 LLM 输出**结构化意图标签**。
2. 条件边根据意图决定路由目标。
3. 必须保留**默认兜底分支**。

```figure kernel
@figures/kernel.json
```

骨架长这样：条件路由从主链上分出知识检索与工具执行两条支路，两条支路的结果统一汇入结果生成， 再经质量审查决定接受、重做还是转人工。阶段三到阶段五做的事，都是往这张图上挂东西。

路由函数本身很短，但它的形状决定了整张图的安全边界：

```python
def route_by_intent(state):
    if state["user_intent"] == "search":
        return "retrieve"
    if state["user_intent"] == "tool_call":
        return "tool_executor"
    if state["user_intent"] == "approval":
        return "human_review"
    return "generate"
```

```figure intent
@figures/intent.json
```

最后那个 `return "generate"` 是关键。它保证了任何未识别、拼写错误、 模型幻觉出来的意图标签都不会让图走进死路。新增一种意图时，只加一条条件边，不动其他节点。

> [!ACCEPT]
> 用 5–10 个典型 query 做端到端验证，图能正确路由到不同分支，**包括人工审批分支**。

## 阶段三：领域知识接入（RAG / 搜索 / 知识库）

> [!GOAL]
> 让 Agent 能获取外部知识，而不是仅依赖模型自身参数。

### 关键动作

#### 把知识获取设计为条件子流程

而不是每次强制检索：

```text
query 构建 → 检索 → 相关性评分 → 注入生成
                ↓ 不相关
             查询重写 → 重新检索
                ↓ 仍无结果
               降级到通用回复
```

```figure rag
@figures/rag.json
```

**核心设计**：让 Agent 自己决定何时检索。检索结果不相关时路由到查询重写，形成自校正循环； 重写后仍无结果则降级到通用回复，而不是强行编造。

#### 数据底座预留

这一阶段先留字段，阶段七再落库：

- **向量库**：文档、切块、embedding、集合。
- **关系库**：文档元数据、权限、版本。
- **对象存储**：原始文件、中间产物。
- **缓存**：热点检索结果、embedding 缓存。

> [!ACCEPT]
> 需要知识检索时分支正确触发；检索结果被注入生成节点； **无相关知识时能降级，而非强行编造**。

## 阶段四：工具与动作集成（MCP / API / CLI）

> [!GOAL]
> 让 Agent 能执行动作，而不仅是生成文本。

### 关键动作

1. **工具来源**：MCP 服务器、HTTP API、CLI 命令。
2. **统一封装**：将工具封装为图节点或工具集，由 Agent 动态选择。
3. **约束到位**：工具节点按下表的七条约束设计。

```figure tools
@figures/tools.json
```

#### 工具节点设计约束

| 约束 | 要求 |
|---|---|
| 超时 | 每个工具独立超时，建议 10–30 秒 |
| 重试 | 有限次重试，指数退避 |
| 幂等 | 非幂等操作需在 State 中记录执行标记 |
| 返回 | 统一封装为 `{status, data, error}` |
| 降级 | 工具失败时返回可解释错误，而非中断全图 |
| 权限 | 工具调用前校验租户 / 角色权限 |
| 审计 | 每次工具调用写入审计日志 |

> [!ACCEPT]
> 意图为工具调用时，图能正确路由到工具节点并完成调用；工具返回结果写回 State； **超时或报错触发降级路径**；**越权调用被拦截**。

## 阶段五：自省与迭代控制

> [!GOAL]
> 建立质量闭环，让 Agent 能审查并改进自己的输出。

### 关键动作

#### 在生成节点之后插入审查节点

对草稿进行多维度评分（准确性、完整性、格式合规性、安全性），评分写入 `quality_score`。

```python
def should_refine(state):
    if state["quality_score"] >= 80:
        return "accept"
    if state["iteration_count"] >= state["max_iterations"]:
        return "fallback"
    return "refine"
```

```figure reflect
@figures/reflect.json
```

#### 关键约束

> [!NOTE]
> 这四条不加，自省就会从「质量闭环」退化成「烧 Token 的死循环」。

- 必须设置**最大迭代次数**，防止死循环。
- 每轮迭代必须有**可度量的增量**，避免空转。
- 达到上限后返回当前最佳结果或「需要人工介入」，而非继续消耗 Token。
- 质量过低且无法自动修正时，可路由到**人工审批节点**。

> [!ACCEPT]
> 低质量输出能被识别并触发修正；修正后评分提升；达到迭代上限时正确降级； **无法自动修正时进入人工闭环**。

# 产品外壳层（阶段六 ～ 阶段九）

外壳层回答「Agent 怎么被用起来」。从这一层开始，代码从一个脚本变成一组服务， 验证方式也从「跑一次看结果」变成「压一遍看指标」。

## 阶段六：后端 API 与会话管理

> [!GOAL]
> 把图从脚本变成服务，让外部可以提交任务、查询状态、流式获取结果。

### 关键动作

#### 接口设计

```text
POST /sessions              创建会话
POST /jobs                  提交任务
GET  /jobs/{id}             查询状态
GET  /jobs/{id}/stream      流式输出（SSE/WebSocket）
POST /jobs/{id}/cancel      取消任务
POST /jobs/{id}/approve     人工审批
POST /jobs/{id}/reject      人工拒绝
GET  /artifacts             获取结果/文件
POST /feedback              反馈
GET  /health                健康检查
GET  /metrics               指标
```

#### 核心机制

- **鉴权**：JWT / OAuth / API Key。
- **限流**：按租户、用户、接口维度。
- **幂等键**：防止重复提交。
- **请求追踪 ID**：贯穿 API → 图 → 工具 → 数据库。
- **会话管理**：绑定 `session_id` 与 checkpointer。
- **错误码**：统一错误结构，区分客户端错误和服务端错误。

```figure api
@figures/api.json
```

注意第 4 步和第 10 步：提交接口**立刻返回 `job_id`**，真正的工作在 Worker 里进行， 结果通过 SSE 回推。这个「提交与执行分离」的形状是阶段八队列化的前提——如果接口一直阻塞到图跑完， 后面就没法把 Worker 拆出去。

```figure jobstate
@figures/jobstate.json
```

每个任务沿着一条确定的状态链前进。两个细节值得现在就定下来： `waiting_approval` 期间图是**挂起**而不是结束的（靠 checkpointer 保存现场）； `failed` 是可重试状态，只有重试耗尽才进死信。

> [!ACCEPT]
> 外部可通过 API 提交任务并获取结果；流式接口能实时推送中间步骤； 鉴权、限流、幂等生效；**请求追踪 ID 可贯穿全链路**。

## 阶段七：数据底座（业务库、向量库、缓存、对象存储）

> [!GOAL]
> 为 Agent 提供持久化、可查询、可审计的数据支撑。

### 关键动作

```figure datastore
@figures/datastore.json
```

#### 关系库（PostgreSQL / MySQL）

```text
users, tenants, roles, permissions
sessions, jobs, job_steps, messages
tool_calls, artifacts, evaluations
audit_logs, configs, model_versions
```

#### 向量库（pgvector / Milvus / Qdrant）

```text
collections, documents, chunks, embeddings
```

#### 缓存（Redis）

```text
会话缓存、限流计数、分布式锁、短期状态、embedding 缓存
```

#### 对象存储（S3 / MinIO / OSS）

```text
上传文件、中间产物、导出结果、附件
```

#### checkpointer

```text
PostgreSQL 或 Redis，支撑断点续接和跨会话恢复
```

> [!ACCEPT]
> 业务数据可持久化；向量检索可用；缓存命中率可观测；文件可上传下载； **checkpointer 可从内存切换到外部存储**。

## 阶段八：持久化队列与任务编排

> [!GOAL]
> 支撑长周期、可恢复、可并发的生产任务。同步 `invoke()` 只适合短任务。

### 关键动作

```figure queue
@figures/queue.json
```

1. **任务队列**：抽象「待执行 Agent 任务」，支持入队、领取、完成、失败重试、死信。
2. **动作队列**：将下游副作用（发消息、写库、调用外部系统）与主流程解耦，单独排队执行。
3. **Worker / Producer 分离**：
   - API 服务：接收请求，写入任务队列。
   - Worker 服务：消费任务，执行 LangGraph。
   - Scheduler：处理定时任务、重试、补偿。
4. **幂等与并发**：每个任务有幂等键；限制并发；设置超时和重试策略。

#### 通用队列表抽象

```text
任务队列：job_id, tenant_id, status, payload, retry_count, created_at, updated_at
动作队列：action_id, tenant_id, status, payload, retry_count, created_at, updated_at
```

> [!ACCEPT]
> 进程重启后任务不丢失；失败可重试；**副作用不重复执行**； 支持并发消费；**状态可恢复**。

## 阶段九：前端交互与人工介入闭环

> [!GOAL]
> 让用户能提交任务、看到过程、审核结果、反馈问题。

### 关键动作

```figure human
@figures/human.json
```

#### 前端最小可用界面

- 任务提交入口
- 流式输出或轮询进度
- 中间步骤展示（意图、检索、工具调用、自省）
- 最终结果展示
- 人工审核 / 修正 / 拒绝按钮
- 配置面板：模型、超时、重试、并发
- 监控面板：成功率、延迟、成本

#### 人工介入闭环

- 高风险动作审批
- 低质量结果人工修正
- 拒绝与重试
- 反馈写回数据库
- 反馈用于评估集和后续微调

> [!ACCEPT]
> 用户可完整走通「提交 → 观察 → 审核 → 反馈」流程； **人工审批能中断并恢复图执行**；反馈数据可查询、可导出。

# 工程运维层（阶段十 ～ 阶段十二）

运维层回答「Agent 怎么管得住」。前两层决定系统能做什么，这一层决定它敢不敢放到生产上。

## 阶段十：安全、权限、审计与多租户

> [!GOAL]
> 让 Agent 在生产环境中可控、可隔离、可追责。

### 关键动作

```figure security
@figures/security.json
```

- **认证**：JWT / OAuth / API Key。
- **授权**：RBAC、多租户隔离、工具级权限。
- **数据隔离**：租户维度隔离业务库、向量库、对象存储、队列。
- **提示注入防护**：输入过滤、系统提示加固、输出校验。
- **PII 脱敏**：日志、轨迹、审计中脱敏。
- **沙箱执行**：CLI / 代码执行类工具在沙箱中运行。
- **审计日志**：谁在什么时候调用了什么工具、产生了什么结果。
- **密钥管理**：环境变量或密钥管理服务，禁止硬编码。

> [!ACCEPT]
> 越权调用被拦截；租户数据互不可见；审计日志可追溯； **敏感信息不落明文**；工具在沙箱中执行。

## 阶段十一：评估体系与 CI 门禁

> [!GOAL]
> 从「能跑」进入「可回归、可部署」。

### 关键动作

```figure evals
@figures/evals.json
```

#### 三层评估

1. **节点级评估**：意图分类准确率、检索召回率、工具调用成功率、自省评分合理性。
2. **端到端评估**：覆盖典型场景、边界场景、对抗场景，评估完整轨迹的任务完成率。
3. **CI 门禁**：每次图结构或提示词变更时自动运行评估，核心指标低于基线则阻止合并。

#### 按需微调分支

微调是分支而不是主路。只有基础模型在特定任务上表现明显不足时才引入：

- 格式不稳定、输出结构不一致 → 用 **SFT**。
- 判断类任务表现不佳 → 用 **DPO**。
- 微调后必须**重新跑评估**，对比节点级指标。

#### 数据飞轮

```figure flywheel
@figures/flywheel.json
```

```text
人工反馈 → 评估集 → 标注 → 微调 → 回归评估 → 上线
```

A/B 实验则用来对比不同提示词、模型、路由策略。注意飞轮的入口是**人工反馈**—— 阶段九那张「反馈写回数据库」的表，在这里才真正被消费掉。

> [!ACCEPT]
> CI 中评估全部通过；核心指标有基线记录；变更后能自动检测性能退化； **反馈数据能回流到评估集**。

# 阶段总览与核心原则

## 阶段总览

| 阶段 | 加入什么 | 核心验收标准 |
|---|---|---|
| 0 | 需求建模 + State 设计 | State 覆盖全流程，含租户 / 用户 / 会话 / 任务标识 |
| 1 | 最小 StateGraph（2 节点） | `invoke()` 无报错返回结果 |
| 2 | 意图识别 + 条件路由 | 典型 query 正确路由到不同分支 |
| 3 | 领域知识接入 | 检索触发正确，无知识时降级 |
| 4 | MCP / API / CLI 工具 | 工具调用成功，超时有降级，越权被拦截 |
| 5 | 自省与迭代控制 | 低质量触发修正，达上限降级或转人工 |
| 6 | 后端 API + 会话管理 | 可提交、可流式、可审批、可追踪 |
| 7 | 数据底座 | 业务库、向量库、缓存、对象存储、checkpointer 可用 |
| 8 | 持久化队列 + 任务编排 | 任务不丢、可重试、可恢复、可并发 |
| 9 | 前端 + 人工介入闭环 | 提交、观察、审核、反馈全流程走通 |
| 10 | 安全、权限、审计、多租户 | 越权拦截、租户隔离、审计可追溯 |
| 11 | 评估 + CI 门禁 | 评估通过，指标有基线，反馈可回流 |
| 12 | 部署 + 可观测 + 成本 + 灰度 | 可持久化、可恢复、可告警、可回滚 |

> **按需分支**：微调放在阶段十一之后，只有基础模型明显不足时才启用。

## 十条核心原则

1. **先状态，后图**：State 设计错了，后面全乱。
2. **每阶段只加一个复杂度**：不要同时接 RAG、工具、队列和前端。
3. **每阶段有验收标准**：跑通再进下一步。
4. **同步跑通再异步化**：先用 `invoke()` 验证逻辑，再用队列和 Worker 支撑生产。
5. **能观测才上生产**：没有轨迹、指标和告警，就不算生产级 Agent。
6. **失败必须可降级**：工具超时、检索为空、评分过低、迭代超限，都要有明确出口。
7. **安全与权限从阶段零开始预留**：租户、用户、权限字段不要等到阶段十才加。
8. **人工闭环是生产标配**：高风险动作和低质量结果必须有人工介入路径。
9. **数据底座先行**：业务库、向量库、缓存、对象存储、checkpointer 是产品化的基础。
10. **成本和灰度要可控制**：Token 预算、模型路由、灰度发布、回滚策略缺一不可。

## 一句话总结

> 先状态，再图，再路由，再知识，再工具，再自省；然后接 API、接数据底座、接队列、接前端、接人工； 最后补安全、评估、部署、成本、灰度。**每一步都可验证，每一步只解决一类问题。**
